# 공고 기반 AI 청약 상담 UX

deterministic consultation engine과 연결된 공고 기반 상담의 presentation 설계를 기록한다. 상담 화면은 자격·단계·점수를 계산하지 않고, `assessApplication()` 결과를 UI contract로 변환해 보여준다.

## 0. 이 기능이 아닌 것

**ChatGPT clone이 아니다.** 목표는 "AI와 대화하는 느낌"이 아니라 **복잡한 공고를 몇 번의 대화로 이해하고 판정·다음 행동까지 연결되는 것**이다. 그래서:

- 답변은 문장만 주지 않고, 판정이 가능해지면 **결론 카드를 문장보다 먼저** 놓는다.
- 질문은 AI가 자유롭게 던지지 않고 **engine의 `suggestedQuestions`를 칩으로** 렌더링한다.
- 근거는 대화에 쏟지 않고 **접어 둔다.**

## 1. 기존 화면과의 관계

앱에는 이미 범용 AI 탭(`app/(tabs)/ai.tsx`)이 있다. 그쪽은 **사용자 상태 기반 범용 코치**이고, 상담은 **특정 공고의 규칙에 근거한 판정 대화**다. 둘을 합치면 "이 답이 어떤 공고 기준인지"가 사라지므로 **분리한다.**

| 화면 | 역할 | 상담과의 관계 |
|---|---|---|
| `/ai` 탭 | 범용 질문, 준비도 코칭 | 그대로 둔다 |
| 공고 상세 | 공고 정보 + 맞춤판정 진입 | **상담 진입 ①** |
| 맞춤판정 결과 | 확정 판정, 조건·서류·근거 | **상담 진입 ②** |
| 준비 단계 | 실행 | 상담의 종착 CTA |

## 2. 상담 진입 두 곳의 역할 구분

**① 공고 상세 → "이 공고 AI에게 물어보기" (판정 *전*)**

아직 아무 정보도 넣지 않은 사람이 "내가 되나?"부터 시작한다. 상담이 필요한 정보를 1~3개씩 모으고, 충분해지면 판정으로 넘긴다. 맞춤판정의 4단계 폼을 다 채울 준비가 안 된 사람을 위한 **낮은 진입 문턱**이다.

**② 맞춤판정 결과 → "이 결과에 대해 물어보기" (판정 *후*)**

이미 결과가 있고 "왜?"를 묻는다. `seededFrom: 'ASSESSMENT_RESULT'`로 시작해 **결론 카드를 이미 들고** 대화를 연다. 정보 수집 단계를 건너뛴다.

즉 상담은 판정의 **앞(수집)과 뒤(설명)** 양쪽에 붙는다.

판정 규칙이 있는 공고에서만 두 진입점을 연다. 규칙이 없는 공고의 상세에는 상담 CTA를 노출하지 않으며, 직접 URL로 접근해도 다른 공고의 규칙으로 대체하지 않는다.

## 3. 상담 화면 IA

```
┌──────────────────────────────────────┐
│ ←  AI 청약 상담                       │  ScreenHeader
├──────────────────────────────────────┤
│ 삼도이동 1지구 …          [검토본 기준]│  context bar (고정)
├──────────────────────────────────────┤
│ (검토본 안내 — 세션당 1회)            │
│                                      │
│              [사용자 질문 말풍선]     │
│                                      │
│ ┌──────────────────────────────────┐ │
│ │ ▌확인할 정보가 더 있어요          │ │  결론 카드 먼저
│ │  공급유형  청년 특별공급          │ │
│ │  공급단계  확인 전                │ │
│ │  가점      점수 확인 전           │ │
│ └──────────────────────────────────┘ │
│ 답변 문장                             │
│ ⌂ 프로필의 …을(를) 사용했어요         │
│ [프로필 정보 수정]                    │
│                                      │
│ ▸ 공고 근거 2건 보기                  │  접힘
├──────────────────────────────────────┤
│ 공고일 기준 나이가 어떻게 되세요?      │  추천 질문 (입력창 바로 위)
│ (만 19~39세)(만 40세 이상)(만 19세…)  │
│ ┌────────────────────────┐  ┌──┐    │
│ │ 이 공고에 대해 물어보세요 │  │ ↑│    │  composer
│ └────────────────────────┘  └──┘    │
└──────────────────────────────────────┘
```

**결론 카드를 문장 위에 둔 이유**: 현장 상담사가 고객과 함께 볼 때 답이 맨 위에 있어야 한다. 문장을 읽어 내려가야 결론이 나오면 화면을 고객에게 돌려 보여줄 수 없다.

**추천 질문을 입력창 바로 위에 둔 이유**: 키보드가 올라와도 함께 따라 올라온다. 대화 흐름 안에 두면 키보드에 가려진다.

## 4. Quick action / 추천 질문

첫 화면 3개: `내가 신청 가능해?` · `필요한 서류는?` · `예외조건 알려줘`
결과 후: `왜 9점이야?` · `필요한 서류는?`

`options`가 있는 질문은 **칩으로 답한다**(만 19~39세 / 만 40세 이상 / 만 19세 미만). 없으면 질문 자체가 칩이 된다. 화면은 최대 **3개**까지만 렌더링한다(`slice(0, 3)`).

## 5. Missing info

한 번에 "나이, 소득, 자산, 통장, 결혼여부 전부 입력하세요"라고 하지 않는다. engine이 `suggestedQuestions`를 1~3개씩 주고, 화면은 그것만 보여준다. 답을 모르면 `잘 모르겠어요` 칩으로 넘어가고 해당 항목은 `unresolved`로 남는다.

## 6. 프로필 재사용

`reusedProfileFacts`가 오면 "프로필의 공고 기준일 거주지(제주특별자치도), 현재 주택소유 여부(무주택)을(를) 사용했어요."로 표시하고 `OPEN_PROFILE` 액션으로 수정 경로를 연다. 이미 아는 것을 다시 묻지 않는다는 느낌이 핵심이다.

## 7. 판정 연결

`AssessmentResult`를 다시 구현하지 않는다. 상담 안에는 **compact 카드**(가능 여부 / 유형 / 단계 / 가점 / 남은 항목)만 두고, 조건별 pass·fail, 서류 목록, 전체 근거는 `OPEN_ASSESSMENT`로 기존 결과 화면에 넘긴다.

## 8. WHY

`왜 9점이야?` → **결론 카드 → 핵심 이유 문장 → 근거 접힘**. 근거를 열면 원문 발췌가 나오고, 내부 `근거 ID`는 그 안에서만 보인다.

## 9. Unresolved

engine이 모르는 것을 오류로 그리지 않는다. `unresolved`는 회색 박스에 **"공고 기준을 추가로 확인해야 하는 항목"**으로 표시한다. 붉은색·경고 아이콘·"실패" 문구를 쓰지 않는다.

## 10. 검토본 표시

- context bar에 **항상** `검토본 기준` 배지
- 세션 시작 시 **한 번만** "공고 검토본을 기준으로 답변해요. 최종 공고에서 조건이 바뀔 수 있어요."
- AI confidence 수치는 표시하지 않는다(사용자·관리자 공통 원칙)

## 11. 무가점

`scoring === 'NOT_APPLICABLE'`이면 `가점제 아님 · 공급단계/추첨`으로 표시한다. `scoreLabel()` 한 곳에서만 판단하므로 0점 카드가 생길 경로가 없다.

## 12. Engine 연결

`engineAdapter.ts`가 domain의 `ConsultationResponse`와 마지막 `ApplicationAssessmentResult`를 presentation contract로 변환한다. 어댑터는 상태·단계·점수·조건을 새로 계산하지 않는다. `blocking`과 `pending`만 기존 condition/missing label을 사람이 읽는 문구로 바꾸고, domain action과 evidence를 UI 형태로 옮긴다.

맞춤판정 결과에서 시작할 때는 메모리 내 일회성 seed에 profile snapshot, answers, result를 복제해 전달한다. 브라우저 저장소나 DB에는 상담 답변을 추가 저장하지 않는다.

**engine이 맞춰야 하는 contract**는 [contract.ts](../features/assessmentConsultation/contract.ts)이며, 화면이 실제로 소비하는 필드는 다음과 같다.

| 필드 | 필수 | 화면에서 하는 일 |
|---|---|---|
| `message` | ✅ | 답변 문장 |
| `assessment.status` | | 결론 카드 헤드라인 |
| `assessment.supplyType` / `stage` | | 카드 행 |
| `assessment.scoring` / `score` | | `scoreLabel()` — 무가점 처리 |
| `assessment.blocking` / `pending` | | "충족하지 못한 / 확인이 필요한 항목 N개" |
| `suggestedQuestions[].options` | | 칩. 없으면 질문 자체가 칩 |
| `actions[].kind` | | `OPEN_ASSESSMENT` / `OPEN_PROFILE` / `OPEN_PREPARATION` / `ANSWER` |
| `evidenceRefs[]` | | 접히는 근거. `label`·`section`·`textExcerpt` 사용 |
| `unresolved[]` | | 확인 필요 박스 |
| `reusedProfileFacts[]` | | 프로필 재사용 안내 |
| `session.sourceStatus` | ✅ | 배지 + 첫 턴 안내 |

**engine과 adapter가 지켜야 하는 것**

- `suggestedQuestions`는 **3개 이하**로 보낸다(화면이 잘라내지만, 자르면 engine 의도가 사라진다).
- `blocking`/`pending`은 **이미 사람이 읽는 문구**여야 한다. 화면은 rule key를 라벨로 바꾸지 않는다.
- 답을 모르면 `message`에 사과를 쓰지 말고 **`unresolved`에 항목을 담는다.**
- `assessment`는 deterministic 판정이 실제로 돌았을 때만 넣는다. 추측으로 카드를 만들면 안 된다.
- 생애최초는 `scoring: NOT_APPLICABLE`, `score: null`로 전달한다.
- 외부 AI provider가 없어도 offline interpreter로 동일한 orchestration을 검증한다.

## 13. MVP에서 하지 않는 것

- 대화 history 저장·채팅방 관리 (현재 공고 한 세션에 집중)
- 상담사 전용 화면 (같은 결과 화면을 더 잘 쓰는 쪽으로)
- 상담 결과의 DB 반영·승인
