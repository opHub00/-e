# 청약 맞춤판정 (ApplicationAssessment)

## 현재 제공 범위

공고별 자격 → 공급유형 → 순서가 있는 공급단계 → 해당 유형의 가점 → 경고·서류·근거를 계산한다.
`assessApplication(rules, { profile, details }, listingId)`는 I/O, AI, 현재 시각에 의존하지 않는 순수 함수다.
AI API와 신규 사용자 스토어는 사용하지 않는다. DB 읽기 기반은 `data/`에 추가했으며 운영 DB 적용과 배포는 별도다.
상세 설계/등록 절차는 [Rule DB 구조](../../docs/application-assessment-data-architecture.md)를 따른다.

**삼도이동 1지구의 공식 입주자모집공고 원문은 저장소에 없었다.**
`samdoReferenceRules`는 사용자 요구에 따른 구조 참조이며, 법적 기준의 전사본이 아니다.
공고일, 금액 한도, 인정기간 기준, 배점은 `null`, 검증 상태는 `REFERENCE_ONLY`다.
따라서 이 참조 공고를 선택하면 `NEEDS_MORE_INFORMATION`, `eligible: null`, `stage: null`이며 점수를 표시하지 않는다. DB에 별도로 승인된 규칙은 해당 버전의 실제 입력조건에 따라 판정한다.
생애최초는 정보가 부족해도 가점이 없는 구조(`NOT_APPLICABLE`)를 유지한다.
실제 공고를 찾거나 이름이 같다는 이유로 이 참조 규칙을 적용하지 않는다.

## 데이터·판정 계약

- 기존 `useUserStore.applicantProfile` / `ApplicantProfileV2`를 그대로 사용한다. 알려진 값만 평가하고 프로필 기본 나이, 통장 개월, 소득·자산 구간을 공고 기준 정확값으로 추정하지 않는다.
- 공고 기준일 거주지는 프로필 거주지를 사용자가 확인한 뒤 사용한다. 별도 입력은 화면 메모리에만 두며 URL, 로그, 저장소, AI로 전송하지 않는다.
- 출생일, 혼인신고일, 거주 시작일, 통장 가입일, 무주택 시작일은 ISO 날짜다. 기간은 고정된 공고일에 대해 완성된 개월을 계산한다. 날짜 형식만 맞는 불가능한 날짜도 거부한다.
- `noHomeSince`는 원문의 인정 기산일을 확인하고 입력하는 값이다. 생일·혼인·처분일에서 자동으로 법적 기산일을 도출하는 기능은 후속 범위다. 제공된 처분일과의 모순은 총점을 숨기고 재확인을 요청한다.
- 프로필의 혼인 상태는 미혼/기혼이며 예비신혼·한부모는 추가 `familyCategory`로 표현한다. 현재 미혼이라는 프로필과 교차 확인한다.
- 태아는 도메인에 별도로 모델링되어 있다. 현재 참조에서 미성년 출생아 수와 합산하지 않으며 태아 인정이 필요한 입력은 특례 확인으로 보낸다.
- 해외 체류 이력이 없다고 확인했을 때만 단순 연속거주기간을 계산한다. 체류 이력이 있거나 미상이면 기간점수를 만들지 않는다.
- 조건식은 JSON 직렬화 가능한 `all`/`any`/`eq`/`gte`/`lte`다. 빈칸은 false가 아니다. 조건 결과는 PASS/FAIL/UNKNOWN이다.
- 단계는 앞에서부터 평가한다. 앞선 단계에 결정적인 실패가 없고 UNKNOWN이 있으면 그 단계에서 멈춘다. 명시적인 실패일 때만 다음 단계로 진행한다.
- 가점 총점과 만점은 항목별 점수·최댓값을 합한다. 미확인·빈 배점표, 해당 입력에 대한 배점 중복/누락, 음수 점수는 총점으로 내보내지 않는다.
- 청년 일반공급의 근로/소득세 기간은 **한 가점항목**이다. 원문에서 확인할 `youth.workPeriodBasis`에 따라 `work` 또는 `tax`를 선택한다. 두 기간을 더하지 않는다. 공고가 다른 산식을 쓰면 fact 계산을 확장해야 한다.
- 특례 검토는 REVIEW로 처리한다. 전체 상태를 확인 필요로 바꾸며, 관련 미달 조건도 함께 보존한다.
- `eligible`은 true / false / null이다. 조건·점수·규칙 부족은 `NEEDS_MORE_INFORMATION`이다. 점수만 부족한 경우 자격 조건과 판별된 단계는 확인 가능하지만 신청 가능으로 요약하지 않는다.
- 결과는 규칙 ID/버전, listing ID, 조건별 입력·기준값, 가점 적용구간, source/section/label/page/url 확장용 evidence를 보존한다.
- `source`, `section`, `page`, `url`은 공고 원문을 확보한 뒤 정확하게 기입한다. 현재 source의 ‘원문 확인 전’ 표시를 공식 출처로 해석하면 안 된다.

## 공급유형

- 청년: 연령, 혼인, 본인 주택 이력, 통장, 소득, 본인·부모 자산, 거주, 제한 검토. 우선공급 3항목, 일반공급 4항목의 배점 구조.
- 신혼부부: 신혼/예비신혼/한부모 분기, 혼인기간·자녀, 무주택세대, 통장, 맞벌이 소득, 세대 자산·거주 검토. 우선 3항목, 일반 4항목.
- 생애최초: 본인·세대 주택 이력, 혼인/자녀, 소득 활동·소득세 이력, 통장·납입금액, 소득·자산·거주 검토. 1/2/3단계만 반환하며 점수는 없다.
- 신생아 등 추가 시 `SupplyType`과 label을 확장하고 `supplies`에 자격·단계·선택적 가점 규칙을 추가한다. 엔진 자체는 유형별 UI 조건문을 사용하지 않는다.

## 실제 공고 활성화 전 TODO

1. 제주개발공사 원문과 정정 공고 확보, 공고 ID·기준일 확정.
2. 자격 항목 자체를 원문과 대조. 모든 금액/기간과 실제 우선공급 대상 조건을 검토자가 전사.
3. 현재 우선공급 `youthPriorityTarget` / `newlywedPriorityTarget` 확인값을 실제 대상 조건식으로 교체. 지금의 확인 질문만으로 운영용 우선공급을 승인하면 안 된다.
4. 가구원수·맞벌이별 소득 기준표, 자산의 합산범위, 근로/세금 인정방식, 태아·한부모 자녀 기준, 무주택 기산일·해외 체류 예외 전사.
5. 실제 배점표와 동점자 처리, 단계별 잔여물량 이월 등을 검토. 현재 단계는 입력조건상의 첫 해당 단계이며 당첨 확률·잔여물량 배정 계산이 아니다.
6. 각 규칙의 원문 section/page/url 등록, 명시적 실제 listing ID 매핑, 실제 사례 회귀테스트 후 출처에 맞게 DRAFT_SOURCE_VERIFIED 또는 OFFICIAL_VERIFIED 버전을 새로 등록·승인.
7. AI가 향후 Rules JSON을 만들더라도 수신 스키마 검증·버전·출처 검토·승인 과정을 거친다. DB 규칙은 codec 검증 후 기존 순수 엔진으로 전달한다. 기존 static fixture는 테스트 및 명시적 reference 선택에만 사용하며 DB 오류 fallback이 아니다.
8. 기존 범위형 프로필에서 정밀 날짜·금액·세대 이력 프로필로 확장할 때 어댑터와 기존 저장·클라우드 마이그레이션을 함께 검토한다.

## 검증

`npm run test:assessment` — 기존 23개 엔진/UX 계약 테스트와 DB repository 테스트. 테스트용 금액·배점은 실제 삼도이동 수치가 아니며 런타임 모듈에서 import하지 않는다.
기존 `npm test`에 포함했다. 새 라이브러리나 lockfile 변경은 없다.

## Claude UX QA 집중 범위

- 모바일 360/390px, 큰 글자에서 홈의 세 진입점이 같은 위계로 읽히는지.
- 5개 하단 탭(홈/청약찾기/맞춤판정/준비/전체), AI의 기존 전체 메뉴·상세 CTA 접근성.
- 홈 진입, 실제 상세에서 listing ID 전달, 미등록/잘못된 ID, 참조 공고로 명시적 전환.
- 프로필 수정 후 복귀, 유형·공고 변경 시 이전 결과/입력이 혼용되지 않는지.
- 긴 추가 질문의 피로도, 숫자 키보드, 빈칸·확인 전·0의 구분, 오류 메시지, 스크린리더 라디오 상태.
- ‘원문 확인 전’ 결과가 신청 가능·실제 점수로 오해되지 않는지.
- 생애최초에서 점수가 없다는 설명, 근거 펼침/접기, 서류와 준비 단계 연결.
- VERIFIED 합성 fixture로 결과 화면을 QA할 경우 반드시 격리된 개발 환경만 사용하고 참조 규칙 또는 배포 번들에 테스트 수치를 넣지 않기.
