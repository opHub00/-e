# AI 추출 Rule 관리자 검수 UX 설계

`ADMIN_REVIEW_READY = NO` 상태에서 작성한 **설계 문서**다. backend, DB mutation, production route 노출은 이 문서의 범위가 아니다.

## 0. 설계 원칙

사용자용 판정 화면과 관리자용 검수 화면은 목적이 반대다.

| | 일반 사용자 | 관리자 |
|---|---|---|
| 목표 | 복잡한 규칙을 **쉽게 이해**하게 | AI가 틀린 규칙을 **가장 먼저 발견**하게 |
| 기본 동작 | 접어 두고 필요할 때 펼침 | **위험한 것을 먼저 펼쳐 둠** |
| 내부 식별자 | 숨김 | 항상 노출 |
| 근거 | 한 단계 뒤 | 원문과 **나란히** |
| 실패 모드 | 너무 어려워서 이탈 | **그냥 승인해 버림** |

관리자 화면의 가장 큰 위험은 "검수했다고 생각했지만 실제로는 통과시킨 것"이다. 따라서 **승인을 쉽게 만들지 않는 것**이 UX 목표다.

## 1. 상태 흐름 (item 29)

```
미분석 → 분석중 → 검수 필요 → 검수중 → 승인 완료 → 활성화 가능 → 활성화
                      ↑                    │
                      └──── 충돌 있음 ←────┘
```

- `충돌 있음`은 별도 분기가 아니라 **어느 단계에서든 되돌아올 수 있는 상태**다.
- `승인 완료 → 활성화 가능` 사이를 분리한다. 전부 승인해도 자동 활성화되지 않는다.
- 현재 benchmark 상태에서는 어떤 공고도 `검수 필요` 이후로 진행할 수 없다.

## 2. 목록 화면 (item 18)

공고 한 줄에 필요한 것만 둔다. rule 수는 정보가 아니다 — **위험 수가 정보다.**

```
삼도이동 토지임대부 국민임대                    검수 필요
공고일 2026.09.14 · 제주도 · VER1.7 검토본 · v3
────────────────────────────────────────────
🚨 반드시 확인 7    ⚠ 확인 권장 24    ✓ 근거 명확 25
충돌 2 · 미해결 예외 11
```

정렬 기본값은 **위험 순**(🚨 개수 → 충돌 수 → 공고일)이다. 이름순이 기본이면 위험한 공고가 목록 아래로 내려간다.

목록에서 승인 동작을 노출하지 않는다. 상세로 들어가야만 승인할 수 있다.

## 3. 상세 정보구조 (item 19)

75개를 평평한 JSON 목록으로 두지 않는다. 2단 grouping.

```
1차: 공급유형   청년 / 신혼부부 / 생애최초 / 공통조건 / 특례
2차: 검수 우선순위   🚨 반드시 확인 / ⚠ 확인 권장 / ✓ 근거 명확
```

기본 펼침 상태는 **🚨만 펼쳐진 상태**다. `✓ 근거 명확`은 접힌 채 개수만 보인다. 관리자가 스크롤로 위험 항목을 찾아내게 하지 않는다.

## 4. 검수 우선순위 매핑 (item 20)

내부 상태 → 표시 상태 변환. 내부 enum은 카드 안에서 별도로 노출한다.

| 표시 | 내부 조건 | 기본 동작 |
|---|---|---|
| 🚨 반드시 확인 | `CONFLICT`, `EXCEPTION_UNRESOLVED`, critical role, `REVIEW_REQUIRED` + 예외 문맥 | 펼침 · 일괄 승인 대상 제외 |
| ⚠ 확인 권장 | `REVIEW_REQUIRED`, 복수 source 결합, 재구성 표(`GEOMETRY_INFERRED`) | 접힘 · 개별 승인만 |
| ✓ 근거 명확 | `AUTO_SAFE_CANDIDATE` (단일 locator · deterministic fact · 예외 marker 없음) | 접힘 |

**`AUTO_SAFE_CANDIDATE`는 자동 승인이 아니다.** 이 이름이 UI에 그대로 나가면 안 된다. 표시는 `근거 명확`이고, 여전히 사람이 눌러야 승인된다.

### Critical rule 가중치 (item 27)

다음 category는 우선순위를 **한 단계 올린다**. `✓ 근거 명확`이어도 `⚠`로 표시한다.

```
소득 · 자산 · 점수 · 무주택 · 통장 · 지역 · 공급단계 · 특례
```

근거가 명확해 보여도 semantic role이 틀리면 판정 결과가 바뀌는 항목들이다. 실제 benchmark에서 `600만원`(저축액)이 자산 한도 후보로 잡힐 수 있는 경로가 확인됐다.

## 5. Rule Review Card (item 21)

한 카드에서 판단이 끝나야 한다. 다른 화면으로 가지 않는다.

```
┌─ 🚨 반드시 확인 ────────────────── 신혼부부 · 소득 ─┐
│ 세대 월평균소득 상한                                │
│                                                     │
│ ┌── 공고 원문 ──────┬── AI 해석 ─────────────────┐ │
│ │ "월평균소득이 전년 │ 대상  신혼부부             │ │
│ │  도 도시근로자 가구│ 단계  일반공급             │ │
│ │  원수별 월평균소득 │ 조건  소득 ≤ 130%          │ │
│ │  의 130% 이하…     │ 값    130 (PERCENT)        │ │
│ │  다만, 맞벌이는    │ 연산  lte                  │ │
│ │  200% 이하"        │ 예외  ⚠ 연결된 예외 없음   │ │
│ └────────────────────┴────────────────────────────┘ │
│                                                     │
│ ⚠ 검증 경고                                         │
│   원문에 "다만"이 있으나 예외 rule이 연결되지 않음  │
│   맞벌이 200% 기준이 별도 rule로 추출되지 않음      │
│                                                     │
│ 근거  <표3-1> · Ⅴ.신청자격 · block b000412          │
│ 내부  NEWLYWED.INCOME.SINGLE_LIMIT / REVIEW_REQUIRED│
│                                                     │
│ [ 승인 ] [ 수정 ] [ 보류 ] [ 제외 ]                 │
└─────────────────────────────────────────────────────┘
```

**원문이 왼쪽, AI 해석이 오른쪽**이다 (item 22). 모바일에서는 원문이 위, 해석이 아래 — 순서를 뒤집지 않는다. 원문을 먼저 읽고 해석을 검증하는 것이지, 해석을 먼저 읽고 원문에서 근거를 찾는 것이 아니다.

AI confidence 수치는 관리자에게도 표시하지 않는다. benchmark에서 HIGH confidence가 안전을 뜻하지 않는다는 것이 이미 확인됐다. 대신 **무엇이 검증됐고 무엇이 안 됐는지**를 문장으로 쓴다.

## 6. Exception 강조 (item 23)

원문에 다음이 있으면 카드에 **강조 표시하고 해당 문구를 하이라이트**한다.

```
단 · 다만 · 제외 · 예외 · 배우자 · 혼인 전 · 출산 · 해외체류 · 특례 · 불구하고 · 한하여
```

규칙:

- 예외 문구가 있는데 `relatedExceptionRuleKeys`가 비어 있으면 **`승인` 버튼을 기본 비활성화**한다.
- 활성화하려면 관리자가 `예외 없음을 확인함` 체크박스를 눌러야 한다. 한 번의 추가 동작이 "무심코 승인"을 막는다.
- 강한 marker(`단,`, `다만`, `제외`)와 문맥 marker(`배우자`, `출산`)를 구분한다. 문맥 marker 단독이면 경고 강도를 낮춘다 — `배우자`만으로 경고하면 수백 건이 잡혀 신호가 죽는다.

## 7. Conflict UX (item 24)

AI가 하나를 고르게 하지 않는다. **둘 다 보여주고 관리자가 고른다.**

```
┌─ 🚨 기준 충돌 — 관리자 확인 필요 ───────────────────┐
│ 지역우선 거주기간 기준일                            │
│                                                     │
│ ① "제주특별자치도 1년 이상 거주"                    │
│    Ⅳ.신청기준 · block b000087                       │
│    [ 이 근거 채택 ]                                 │
│                                                     │
│ ② "최초 입주자모집공고일 현재 거주"                 │
│    <표2> 지역우선 공급기준 · cell t012:3:1          │
│    [ 이 근거 채택 ]                                 │
│                                                     │
│ [ 둘 다 보류하고 원문 재확인 ]                      │
└─────────────────────────────────────────────────────┘
```

- 기본 선택 없음. `resolution: null`, `requiresReview: true`를 UI가 그대로 반영한다.
- 충돌이 미해결인 공급유형은 **활성화 단계로 진행 불가**하다.

## 8. 관리자 Action (item 25)

| 동작 | 의미 | 결과 |
|---|---|---|
| 승인 | 이 rule을 그대로 사용 | `APPROVED` |
| 수정 | 값·연산자·단계·대상을 관리자가 고침 | `APPROVED_WITH_EDIT` + 수정 이력 |
| 보류 | 판단 불가, 추가 확인 필요 | `HELD` — 활성화 차단 |
| 제외 | 이 rule을 쓰지 않음 | `REJECTED` |

`수정`은 원문 근거를 바꾸지 못한다. 값만 고치고 locator는 유지한다. 관리자가 원문에 없는 값을 넣으면 그건 추출이 아니라 창작이므로, **수정 시 원문 대조 패널을 강제로 펼친다.**

이번 작업에서는 UI state까지만 구현한다. DB mutation 없음.

## 9. 일괄 승인 안전장치 (item 26)

`전체 승인` 버튼을 만들지 않는다. 대신 **범위가 한정된 일괄 동작**만 둔다.

```
[ ✓ 근거 명확 25개 한 번에 승인 ]
   └ 아래를 포함하면 버튼이 비활성화된다
      · CONFLICT
      · UNRESOLVED / EXCEPTION_UNRESOLVED
      · 예외 문구가 있으나 미연결
      · critical role (소득·자산·점수·무주택·통장·지역·단계·특례)
```

비활성화 시 **이유를 문장으로 보여준다**: "소득·자산 rule 6개가 포함되어 있어 한 번에 승인할 수 없어요. 개별로 확인해 주세요."

버튼을 회색으로만 만들고 이유를 말하지 않으면 관리자는 우회 경로를 찾는다.

## 10. Source provenance (item 28)

관리자 화면 하단에 **항상** 노출한다. 고객 화면에는 없다.

```
공고문      삼도이동 토지임대부 국민임대 VER1.7 검토본
문서 버전   VER1.7 · 2026.09.14
source URL  https://…
문서 hash   sha256:bd67d7ee…12e8763
추출 시점   2026-09-18 16:43 KST
추출 버전   assessment-rule-extraction-v3 / PLAN_B_24
parser      document-parser-v1 · 4,115 block · 172 table
```

문서 hash가 바뀌면 **기존 검수 결과를 자동으로 무효화**하고 `검수 필요`로 되돌린다. 같은 공고라도 파일이 바뀌면 다른 문서다.

## 11. 사용자 화면과 공유하는 것 / 공유하지 않는 것

| | 사용자 | 관리자 |
|---|---|---|
| 규칙 이름(`label`) | ✅ | ✅ |
| 원문 발췌(`textExcerpt`) | 2단계 뒤 | 항상, 좌측 고정 |
| 내부 rule ID | ❌ | ✅ |
| locator / block ID | ❌ | ✅ |
| 문서 hash | ❌ | ✅ |
| AI confidence | ❌ | ❌ (양쪽 모두) |
| source status | ✅ 사람 말로 | ✅ enum 포함 |

## 12. backend 연결 전에 필요한 것

이 UX가 동작하려면 현재 데이터에 없는 것이 있다.

1. **rule별 검수 상태 저장소** — `APPROVED / APPROVED_WITH_EDIT / HELD / REJECTED` + 검수자 + 시각.
2. **`requiredDocuments`의 분류** — 현재 `string[]` 평면 목록이라 `필수 / 상황별 / 추가 확인` 구분이 불가능하다. 사용자 화면의 서류 grouping(item 14)도 이것이 있어야 가능하다. 지금은 개수 표시 + 접기로만 처리했다.
3. **conflict의 구조화된 표현** — 현재 v2 artifact의 `conflicts`는 비어 있고 정규식 판정에 의존한다. 두 근거를 나란히 놓으려면 `{concept, candidates: [{value, sourceId, locator}], resolution: null}` 형태가 필요하다.
4. **예외 관계의 양방향 조회** — 현재 `relatedExceptionRuleKeys`는 base → exception 단방향이고, 56개 중 3개만 채워져 있다. 고아 예외 26개를 화면에 띄우려면 역방향 색인이 필요하다.
5. **문서 hash 변경 감지 훅** — 재검수 트리거.
6. **관리자 인증·권한** — 현재 앱에 관리자 역할 개념이 없다.

`ADMIN_REVIEW_READY = YES` 이전에는 1~6 중 어느 것도 production에 연결하지 않는다.
